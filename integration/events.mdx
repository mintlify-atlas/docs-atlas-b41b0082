Console's communication model is asynchronous and network-driven. When an admin issues a command to a player running your mod, Console delivers that command over its own network layer — not through Photon or Gorilla Tag's built-in RPC system. Some commands are fire-and-forget (they execute silently on the receiver), but others trigger an **event response** that travels back to the sender. Understanding how these response events work is essential for building admin tooling on top of Console.

## How the Event Model Works

Commands flow in one direction: from an admin with authority, outward to connected receivers. Certain commands instruct the receiver's Console instance to send a reply event back across the network. These reply events arrive **asynchronously** — there is no blocking call or callback return value. Your embedded copy of Console handles incoming events via the `HamburburData` component's update loop.

<Note>
  Only commands issued by an admin who holds authority over your mod's Console network identity will cause events to fire on a receiver. Messages from non-admin users are silently ignored by Console before they ever reach your handler code.
</Note>

## The `isusing` / `confirmusing` Handshake

The only documented event response in Console is the presence check. An admin sends the `isusing` command to a target player. If that player is running a mod with Console embedded, their Console instance automatically replies with a `confirmusing` event that includes the **mod name** configured in `Console.cs`. This lets admins discover which Console-enabled mods are active in a room without requiring any manual player reporting.

### Flow Diagram

<Steps>
  <Step title="Admin sends isusing">
    An admin calls `Console.ExecuteCommand("isusing")` targeting a specific player. The command is dispatched over the Console network to that player's game client.

    ```csharp
    // Admin side — executed with appropriate authority
    Console.ExecuteCommand("isusing");
    ```
  </Step>

  <Step title="Receiver's Console replies automatically">
    On the receiver's client, Console intercepts the `isusing` command internally and fires a `confirmusing` event back toward the sender. **No custom code is required on the receiver's side** — this reply is built into the Console library.

    The event payload contains the mod name string you set in the `#region Configuration` block of `Console.cs`.
  </Step>

  <Step title="Admin receives confirmusing and reads the mod name">
    Back on the admin's client, the `confirmusing` event arrives asynchronously. How you receive and handle this event depends on the event wiring inside your embedded copy of Console — consult the `#region Configuration` block in `Console.cs` for the precise mechanism exposed in your version.

    When the event arrives, the payload contains the mod name of the responding client:

    ```csharp
    // Conceptual example — your event handler receives the confirmusing payload
    void YourEventHandler(/* parameters depend on your Console version */)
    {
        // The payload contains the mod name of the responding client
        string modName = /* extract from payload */;
        Debug.Log($"[Console] Detected Console user running: {modName}");
    }
    ```

    <Note>
      The exact event handler signature and registration method are defined inside the Console source files you embedded. Refer to the `#region Configuration` block in `Console.cs` for the delegate type and any additional event fields available in your copy.
    </Note>
  </Step>
</Steps>

## Handling Events in Your Plugin

Your event handler code should be wired up after `Console.LoadConsole()` is called. The `HamburburData` component processes Console network packets each frame and delivers events on the main Unity thread, so it is safe to call Unity APIs directly inside your handler.

```csharp
void Start()
{
    Console.LoadConsole();
    gameObject.AddComponent<HamburburData>();
    gameObject.AddComponent<TrackerManager>(); // Optional but recommended

    // Wire up your event handler here — after Console is initialized
    // Refer to Console.cs for the specific registration API in your embedded copy
}
```

Because events arrive at an indeterminate time after a command is sent, you should **never block** waiting for a response. Use flags, queues, or coroutines if your logic needs to act once a reply arrives.

```csharp
// Example: use a flag to act once confirmusing is received
private bool _consoleUserDetected = false;

// Conceptual handler — signature matches whatever Console.cs defines
void YourEventHandler(/* parameters depend on your Console version */)
{
    // Check for confirmusing event and record the mod name
    _consoleUserDetected = true;
}
```

<Info>
  Because the Console network is separate from Gorilla Tag's Photon layer, event latency depends on Console's own backend rather than the room's Photon ping. Expect slight variance in delivery time based on network conditions.
</Info>
