Console's communication model is asynchronous and network-driven. When an admin issues a command to a player running your mod, Console delivers that command over its own network layer — not through Photon or Gorilla Tag's built-in RPC system. Some commands are fire-and-forget (they execute silently on the receiver), but others trigger an **event response** that travels back to the sender. Understanding how these response events work is essential for building admin tooling on top of Console.

## How the Event Model Works

Commands flow in one direction: from an admin with authority, outward to connected receivers. Certain commands, however, instruct the receiver's Console instance to send a reply event back across the network. These reply events arrive **asynchronously** — there is no blocking call or callback return value. Instead, you register handlers in your `BaseUnityPlugin` class after calling `Console.LoadConsole()`, and Console invokes those handlers whenever a matching event is received.

<Note>
  Only commands issued by an admin who holds authority over your mod's Console network identity will cause events to fire on a receiver. Messages from non-admin users are silently ignored by Console before they ever reach your handler code.
</Note>

## The `isusing` / `confirmusing` Handshake

The most commonly used event flow is the presence check. An admin sends the `isusing` command to a target player. If that player is running a mod with Console embedded, their Console instance automatically replies with a `confirmusing` event that includes the **mod name** configured in `Console.cs`. This lets admins discover which Console-enabled mods are active in a room without requiring any manual player reporting.

### Flow Diagram

<Steps>
  <Step title="Admin sends isusing">
    An admin calls `Console.ExecuteCommand("isusing")` targeting a specific player. The command is dispatched over the Console network to that player's game client.

    ```csharp
    // Admin side — executed with appropriate authority
    Console.ExecuteCommand("isusing");
    ```
  </Step>

  <Step title="Receiver's Console replies automatically">
    On the receiver's client, Console intercepts the `isusing` command internally and fires a `confirmusing` event back toward the sender. **No custom code is required on the receiver's side** — this reply is built into the Console library.

    The event payload contains the mod name string you set in the `#region Configuration` block of `Console.cs`.
  </Step>

  <Step title="Admin receives confirmusing and parses the mod name">
    Back on the admin's client, the `confirmusing` event arrives asynchronously. Register a handler after `Console.LoadConsole()` to capture this event and read the mod name from the payload:

    ```csharp
    void Start()
    {
        Console.LoadConsole();
        gameObject.AddComponent<HamburburData>();
        gameObject.AddComponent<TrackerManager>();

        // Register a handler for incoming Console events
        Console.OnEventReceived += HandleConsoleEvent;
    }

    void HandleConsoleEvent(string eventName, string payload)
    {
        if (eventName == "confirmusing")
        {
            // payload contains the mod name of the responding client
            string modName = payload;
            Debug.Log($"[Console] Detected Console user running: {modName}");
        }
    }
    ```

    <Note>
      The exact event handler signature (`Console.OnEventReceived`) follows the pattern established in the Console source. Consult the `#region Configuration` block in `Console.cs` for the precise delegate type and any additional event fields exposed in your embedded copy.
    </Note>
  </Step>
</Steps>

## Registering Event Handlers

All event handlers must be registered **after** `Console.LoadConsole()` is called. Registering before initialization may result in handlers being overwritten or silently dropped during the Console startup sequence.

```csharp
void Start()
{
    Console.LoadConsole();
    gameObject.AddComponent<HamburburData>();
    gameObject.AddComponent<TrackerManager>(); // Optional but recommended

    // Safe to register handlers here — Console is initialized
    Console.OnEventReceived += HandleConsoleEvent;
}

void OnDestroy()
{
    // Always unsubscribe to avoid memory leaks when the plugin unloads
    Console.OnEventReceived -= HandleConsoleEvent;
}

void HandleConsoleEvent(string eventName, string payload)
{
    switch (eventName)
    {
        case "confirmusing":
            // A user confirmed they are running a Console-enabled mod
            // payload = the mod name they reported
            break;

        default:
            // Handle or log any other events your mod cares about
            break;
    }
}
```

<Tip>
  Unsubscribe from `Console.OnEventReceived` in `OnDestroy()`. BepInEx plugins are long-lived objects, but if your scene or plugin is ever torn down, dangling delegates can cause `NullReferenceException` errors during event dispatch.
</Tip>

## Events Are Asynchronous

Console delivers events on the main Unity thread via the `HamburburData` component's update loop, so it is safe to call Unity APIs (including `Debug.Log`, `GameObject` operations, and UI updates) directly inside your handler. However, because events arrive at an indeterminate time after a command is sent, you should **never block** waiting for a response. Use flags, queues, or coroutines if your logic needs to act once a reply arrives.

```csharp
// Example: use a flag to act once confirmusing is received
private bool _consoleUserDetected = false;

void HandleConsoleEvent(string eventName, string payload)
{
    if (eventName == "confirmusing")
    {
        _consoleUserDetected = true;
        // Optionally start a coroutine or update UI here
    }
}
```

<Info>
  Because the Console network is separate from Gorilla Tag's Photon layer, event latency depends on Console's own backend rather than the room's Photon ping. Expect slight variance in delivery time based on network conditions.
</Info>
